# 一次做对 · 成功复用 · 纠错与防再犯

本页是软件团队 Agent 的**质量宪法**。目标不是「多改几轮碰巧绿」，而是：

1. **一次开发就成功**（First-time-right）  
2. **成功经验可复用**  
3. **有纠错闭环**  
4. **同类问题不得犯第二次**

Token、并行数量不是约束；**正确性与组织记忆**才是约束。

---

## 1. 评估：当前 kit 已覆盖 / 仍缺什么

| 能力 | 已有 | 缺口（本次补齐） |
|------|------|------------------|
| 验收与证据 | Verifier、任务卡、VERIFY | 实现前强制「可一次做对」检查单 |
| 边界防改坏 | Feature Map、不能破坏 | 与失败案例库双向绑定 |
| 角色分离 | Spec / Backend / Debug / Verifier | 主控拒绝「无 Spec 就编码」 |
| 成功复用 | 示例与模板 | **Success Playbook** 目录约定 |
| 纠错 | FAIL 退回 | **Failure Record** 强制归档 |
| 防再犯 | 口头「下次注意」 | 写入 Feature Map / Skill 前不得标 Done |

**结论：** 工具链方向对，但若没有「失败入库 + 成功入库 + 开干前读库」，仍会反复踩坑。一次做对 = **开干前约束 + 验收门 + 事后记忆** 三件套，缺一不可。

---

## 2. 一次做对（First-time-right）门禁

主控在任务进入 **Doing** 前必须全部满足，否则保持 Backlog/Blocked：

### 2.1 Spec 门（没有就不准写代码）

- [ ] 目标一句话清晰  
- [ ] 验收标准 ≥ 1 条且**可判定**（能写出通过/失败）  
- [ ] 「不能破坏」已列出或显式写「无回归面」  
- [ ] 验证命令或固定复现步骤已写  
- [ ] 允许改 / 禁止改 的范围已写  
- [ ] 待确认问题为 0，或用户已书面确认  

### 2.2 记忆门（开干前读库）

- [ ] 已检索 `docs/failures/` 是否有同类关键词/模块  
- [ ] 已读相关 Feature Map  
- [ ] 若有 Success Playbook，已引用其步骤  

### 2.3 实现门（Backend）

- [ ] 最小 diff；不顺手重构  
- [ ] 不靠改测试定义来变绿（改测试须单独批准）  
- [ ] 交付必含验证输出  

### 2.4 验收门（Verifier）

- [ ] 无证据 → BLOCKED，不得 PASS  
- [ ] PASS 后主控才可标 Done  

**「反复修改」的定义：** 同一任务卡因**同一类根因**第 2 次 FAIL，主控必须升级：停写代码 → 补 Failure Record → 更新 Feature Map/Skill → 再开新一轮实现。禁止在同一理解水平上盲改。

## 3. 成功经验复用（Success Playbook）

当任务 **Verifier PASS** 且你认为可复用时，主控或你触发归档：

**路径建议：** `docs/playbooks/<主题>.md`

```markdown
# Playbook：<名称>

## 适用场景
（什么时候用这条，什么时候不用）

## 前置条件
- Spec / 环境 / 权限

## 标准步骤
1. ...
2. ...

## 验收标准模板
- ...

## 验证命令
```bash

```

## 参考任务 / PR
- ...

## 禁忌（从失败反推）
- ...
```

**规则：** 同类新任务，Spec/主控应优先「套 Playbook 再裁剪」，而不是从零聊天设计流程。

## 4. 纠错与防再犯（Failure Record）

### 4.1 何时必须建 Failure Record

- Verifier **FAIL** 且根因已查清  
- 线上/本地回归：「改好了 A 坏了 B」  
- 同一任务第 2 次因同类原因失败  
- 用户指出 Agent 重复犯的错误  

### 4.2 模板路径

`docs/failures/YYYYMMDD-<短标题>.md` 或按模块 `docs/failures/<module>/...`

```markdown
# Failure：<短标题>

- 日期：
- 任务 ID / 模块：
- 严重度：P0 / P1 / P2

## 现象
（用户或测试看到什么）

## 错误做法（Agent 做了什么）

## 根因（一句话 + 证据）

## 正确做法

## 防再犯（必须落地一项以上）
- [ ] 更新 Feature Map：路径 ____
- [ ] 新增/改测试：____
- [ ] 写入 Skill / Playbook 禁忌：____
- [ ] 更新任务模板默认验收项：____

## 验证防再犯有效
（命令或检查项；以后开干前主控应能搜到本条）
```

### 4.3 硬规则：没有防再犯落地，Done 无效

主控不得将「仅口头总结」的失败任务彻底关闭。  
**Done 的前提：** Verifier PASS **且**（若曾 FAIL）Failure Record 的「防再犯」至少一项已勾选完成。

### 4.4 同样问题不能犯第二次

| 机制 | 作用 |
|------|------|
| 开干前搜 failures | 同模块/同关键词命中 → 任务卡必须引用该 Failure |
| Feature Map「常见失败模式」 | 实现前强制阅读 |
| 回归测试 | 把失败变成可自动红的用例 |
| Verifier 清单 | 把曾经漏验的项写进默认验收/回归 |
| 主控升级策略 | 同类第 2 次 FAIL → 禁止继续堆补丁，先改记忆再实现 |

## 5. 主控行为补丁（写入 Orchestrator 时应遵守）

1. **拒绝无 Spec 编码。**  
2. **Doing 前执行记忆门。**  
3. **FAIL → 查根因 → Failure Record → 再指派实现。**  
4. **同类二犯 → 停工改体系（Map/Skill/测试），不继续蛮干。**  
5. **PASS → 询问是否沉淀 Playbook（高复用场景默认是）。**  
6. **看板增加字段：** `失败归档` / `Playbook` 链接。

---

## 6. 与「反复改坏正常功能」的对应

你的核心痛点是边界不清与回归。一次做对在这里的含义是：

- 改前：Feature Map + 不能破坏 + failures 检索  
- 改中：最小 diff  
- 改后：回归命令证据 + Verifier  
- 改坏后：Failure Record **必须**写回 Map 与测试，否则体系认为问题仍开放  

这样「成功路径」进 Playbook，「失败路径」进 failures，下一次 Agent 没有「忘记上次教训」的资格。

---

## 7. 最小落地顺序（仍坚持一次做对）

1. 主控 + Verifier + 本页门禁（不先堆很多专家）。  
2. 建空目录：`docs/failures/`、`docs/playbooks/`。  
3. 第一次真实 FAIL 就写满一条 Failure Record 并改 Feature Map。  
4. 第一次干净 PASS 的重复型任务写一条 Playbook。  
5. 再扩展 Backend/Debug 并行。  

并行与多专家是加速器；**记忆与门禁**才是一次做对的底座。
