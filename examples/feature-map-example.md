# Feature Map 示例

Feature Map 的作用：告诉 Agent「这个功能是什么、入口在哪、能改什么、绝对不能动什么」。  
改代码前先读对应 Feature Map，能显著降低「改着改着把正常功能改坏」的概率。

建议放在项目里：`docs/features/` 或 `features/` 目录，一个功能一份。

---

## 模板结构

```markdown
# 功能名称

## 目的
一句话说明这个功能解决什么问题。

## 用户路径 / 入口
- 路由或页面：
- 入口操作：
- 关键 UI 元素（可用 testid / 文案描述）：

## 核心行为（预期）
1. ...
2. ...
3. ...

## 代码入口（导航用，以实际代码为准）
- 主要文件：
- 状态/数据来源：
- 相关 API / 服务：

## 边界与约束
### 可以改
- ...

### 绝对不能动
- ...

### 隐式约定（容易被 Agent 忽略的规则）
- ...

## 回归检查清单
改动本功能后，至少验证：
- [ ] ...
- [ ] ...
- [ ] ...

## 常见失败模式（可选，持续更新）
- 现象 → 原因 → 应避免的做法

## 维护说明
路由、选择器、行为变更时，请同步更新本文档。
```

## 完整示例：用户列表筛选

```markdown
# 用户列表筛选

## 目的
在用户管理页按状态（全部 / 已启用 / 已停用）过滤用户列表，并在刷新后保持筛选条件。

## 用户路径 / 入口
- 路由：`/admin/users`
- 入口：顶部状态筛选下拉框
- 关键元素：
  - 筛选器：`[data-testid="user-status-filter"]`
  - 列表行：`[data-testid="user-row"]`

## 核心行为（预期）
1. 默认「全部」：启用 + 停用用户都显示
2. 选择「已停用」：只显示 status=disabled 的用户
3. 选择「已启用」：只显示 status=enabled 的用户
4. 刷新页面后，当前筛选值与列表结果保持一致
5. 与搜索、分页同时使用时，筛选条件仍然生效

## 代码入口（导航用）
- 前端列表与筛选：`src/features/users/UserList.tsx`
- 筛选状态：`src/features/users/userListStore.ts`
- 列表请求：`src/api/users.ts` → `fetchUsers({ status, keyword, page })`
- 后端过滤：用户查询服务中对 status 的处理

## 边界与约束
### 可以改
- 用户列表页的筛选 UI 与请求参数组装
- 与 status 筛选直接相关的查询逻辑

### 绝对不能动
- 登录 / 鉴权 / 权限判断
- 用户创建、编辑、删除的核心流程（除非任务明确要求）
- 其他页面的列表组件（如订单列表）

### 隐式约定
- status 的合法值只有：`all` | `enabled` | `disabled`（前端用 all，后端可能省略或传空表示全部）
- 筛选变化时应重置到第 1 页，避免空页
- 搜索 keyword 与 status 是 AND 关系，不是互相覆盖

## 回归检查清单
- [ ] 全部 / 已启用 / 已停用 三种筛选结果正确
- [ ] 刷新后筛选与列表一致
- [ ] 搜索 + 筛选同时使用正确
- [ ] 分页在筛选后仍正常，总数正确
- [ ] 行内「启用/停用」操作后列表表现符合预期

## 常见失败模式
- 现象：选「已停用」仍看到启用用户  
  原因：前端传了参数但后端未过滤，或参数名不一致  
  应避免：只改 UI 文案不改请求参数；不经验证就认为「传了就对了」

- 现象：筛选后翻页为空  
  原因：改筛选时未重置 page  
  应避免：只更新 status 忘记重置分页

## 维护说明
路由、testid、status 枚举或请求契约变更时，请同步更新本 Feature Map。
```

---

## 使用建议

1. **先写最容易被改坏的 2～3 个模块**，不要追求一次写完全站。
2. **「绝对不能动」和「隐式约定」最重要**，这两块能直接减少回归。
3. 在任务模板的「相关 Feature Map」里写上路径，要求 Agent 先读再改。
4. 每次真实发生「改坏了」，把原因补进「常见失败模式」，形成正向循环。
