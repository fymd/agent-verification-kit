# WorkBuddy 落地：软件团队专家组

## 一、创建 5 个「我的专家」

路径：**专家·技能·连接器 → 专家 → 我的专家 → 创建专家**

| 顺序 | 显示名称 | 提示词来源 |
|------|----------|------------|
| 1 | 研发主控 | [orchestrator.md](orchestrator.md) 复制区 |
| 2 | 需求规格专家 | [experts/spec.md](experts/spec.md) |
| 3 | 后端实现专家 | [experts/backend.md](experts/backend.md) |
| 4 | 问题排查专家 | [experts/debug.md](experts/debug.md) |
| 5 | 验收专家 | [experts/verifier.md](experts/verifier.md) |

创建时名称先定好（创建后不能改）。人设用「是谁 + 边界」，提示词贴完整复制区。

### 创建对话可直接粘贴的示例（验收专家）

```text
请创建专家：
- 名称：验收专家
- 人设：专注软件交付验收，不写业务代码
- 擅长：根据验收标准与测试证据判定 PASS/FAIL/BLOCKED
- 不做：实现功能、在证据不足时放行
- 提示词：（粘贴 team/experts/verifier.md 系统提示词全文）
```

主控、Backend 等同理，只换名称与对应 md。

## 二、推荐协作方式（单人操作）

**日常只召唤「研发主控」。**

1. 你对主控说目标（可附仓库路径、Feature Map、日志）。
2. 主控输出任务卡 + 看板，并给出「请交给某某专家」的指令块。
3. 你新开对应专家会话，粘贴指令块（或 @ 文件）。
4. 专家交付后，把结果贴回主控；主控再生成给验收专家的材料。
5. 验收 PASS 后主控更新看板；FAIL 则生成退回指令。

这样主控真正控制**质量门与进度**，你负责搬运与决策点。

## 三、若使用专家团

若 WorkBuddy 支持自建专家团 / Team 型：

- **团长** = 研发主控（orchestrator 提示词）
- **成员** = Spec、Backend、Debug、Verifier

在团说明里写死：

- 实现结果必须经验收专家；团长不得跳过验收标完成
- 同一模块同时仅一个实现向成员
- 高风险变更必须暂停等用户

专家团积分通常高于单专家，适合已经跑顺流程后使用。

## 四、与 Skill 的配合

| 能力 | 建议 |
|------|------|
| 项目验证命令 | 用 `skills/project-verification-skill.md` 做成/写入项目 VERIFY.md |
| 任务卡 | 复制 `team/task-card.md` 当快捷提示 |
| 读本地代码跑测试 | 给 Backend/Debug 配置所需 Skill/权限；Verifier 可只读你粘贴的证据 |

## 五、对主控说的第一句话模板

```text
你是研发主控。技术栈以 Python/Go 为主。
请按团队流程管理：Spec → 实现/排查 → 验收，用任务卡和看板同步。

本次目标：
<一句话>

已知信息：
- 仓库/路径：
- 相关 Feature Map（如有）：
- 复现或约束（如有）：

请先给出：任务拆分、首张任务卡、需要我确认的问题；不要直接写大段业务代码。
```
