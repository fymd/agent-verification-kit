# 带边界保护的通用任务模板

> 每次给 Builder Agent 下任务时，复制本模板并填写。  
> 目标：减少人工介入、防止改坏正常功能、让 Verifier 有明确检查依据。

---

```markdown
## 允许修改的范围（边界）
- 可以改的文件/目录：

- 绝对不能动的文件/模块：
- 其他约束（最小改动、不引入新依赖、不改公开 API 等）：

## 验证方式（Builder 完成后必须执行并附证据）
1. 命令/测试：
2. 手动步骤：
3. 预期输出或现象：

## 交付要求
- 改动说明：改了哪些文件、为什么这样改
- 证据：测试输出 / 日志 / 复现结果（文字即可）
- 完成后交给 Verifier 做正式验收，不要自行宣布「完成」

## 额外原则（可选但推荐）
- 先读相关代码和 Feature Map，再动手
- 优先最小 diff
- 发现验收标准有歧义时先提问，不要猜测
```

## 填写示例（参考）

```markdown
## 任务目标
修复用户列表页在筛选「已停用」状态时仍显示已启用用户的问题。

## 背景 / 上下文
- 相关模块：用户管理 / 列表筛选
- 相关 Feature Map：examples 或 docs/features/user-list.md
- 已知问题：前端传 status=disabled，后端可能未正确过滤

## 验收标准（Acceptance Criteria）
1. 选择「已停用」时，列表只显示 status=disabled 的用户
2. 选择「全部」时，启用和停用用户都显示
3. 刷新页面后筛选条件保持，结果仍正确

## 不能破坏（回归保护）
- 用户搜索（按姓名）：输入关键字仍能正确过滤
- 分页：切换页码数据正确，总数正确
- 启用/停用操作：列表中的操作按钮仍可用

## 允许修改的范围（边界）
- 可以改：用户列表相关的前端筛选逻辑、对应 API 查询参数处理
- 绝对不能动：用户权限模块、登录/鉴权、其他列表页
- 约束：最小改动；不新增依赖；不改公开 API 契约（除非必要并说明）

## 验证方式
1. 本地启动后打开用户列表
2. 筛选「已停用」→ 确认只出现停用用户
3. 筛选「全部」→ 确认两类都有
4. 刷新 → 确认筛选与结果仍正确
5. 顺带点一次搜索和分页，确认未破坏

## 交付要求
- 说明改了哪些文件及原因
- 附上验证步骤的实际结果
- 交给 Verifier 验收
```

---

## 使用技巧

1. **验收标准要可判定**：避免「体验更好」「更合理」这种主观描述。
2. **「不能破坏」写你最怕被改坏的 2～4 条**，并给出能复现的路径。
3. **边界尽量具体**：写文件路径或模块名，比写「相关代码」有效得多。
4. **Builder 完成后强制走 Verifier**：你只看 PASS/FAIL，而不是每一行 diff。
